## Стек и работающая архитектура

React 19 / Vite / Node 24; FastAPI / Python 3.12 / SQLAlchemy / psycopg.
Managed Neon Auth через официальный @neondatabase/auth; OpenAI Responses API.
SQLite используется в изолированных тестах и локальной разработке.

- Регистрация, вход, выход, восстановление и подтверждение по OTP реализованы через Neon Auth.
- API принимает Bearer JWT: EdDSA, фиксированный JWKS, issuer origin, exp/iat/sub.
  Анонимные токены отклоняются. Пароли и длительные сессии остаются у провайдера.
- Задания, план, Tutor, тесты, результаты и карта ограничены owner_id.
- Чужие ID дают 404. Идемпотентность запросов ограничена владельцем.
- Настройки и черновики браузера разделены по аккаунтам; выход очищает приватный кэш.
- Дневные AI-лимиты в БД: 20 запросов на пользователя, 100 на сервис.
- На публичном сервере обязательно PostgreSQL; он не переключается незаметно на временный SQLite.
- В логах ошибок OpenAI сохраняются только разрешённые коды/типы и статус.
  Ключи, исходные ответы провайдера, фото и учебные тексты не логируются этой диагностикой.

## Исправление пользовательского входа

Сообщение «Войди в свой аккаунт ещё раз» воспроизведено с установленным SDK Neon 0.6:
после getSession() вызов token() получает сохранённую сессию вместо обычного ответа
/token. JWT находится в data.session.token, внедрённый SDK из заголовка set-auth-jwt.
Приложение теперь поддерживает обе формы ответа; непрозрачный session cookie не
передаётся как Bearer JWT. Проверка подписи и владельца на сервере сохранена.

Регрессионный тест с настоящим SDK сначала воспроизвёл отказ старого кода,
после исправления прошли все 10 клиентских тестов. Реальный Neon возвращает
и открывает браузеру set-auth-jwt; этот JWT принят /api/auth/me со статусом 200.
Публичный JS-файл после Live совпал по SHA-256 с проверенной локальной сборкой.
Повторный вход непосредственно на устройстве пользователя ещё ожидает подтверждения.
